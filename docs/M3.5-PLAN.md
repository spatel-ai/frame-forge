desktops, as a dedicated priority milestone, with the steps split so several agents build at once.

## Device matrix

| Device class | Widths checked (px) | Layout |
| --- | --- | --- |
| Small phone | 320, 360 | Phone |
| Phone | 390, 430 | Phone |
| Phone held sideways | 667 × 375, 844 × 390 | Phone |
| Tablet upright | 768, 820 | Tablet (icon sidebar) |
| Tablet held sideways, small laptop | 1024, 1180 × 820, 1280 | Desktop |
| Desktop | 1440, 1920 | Desktop |

Each width runs in Chromium and in WebKit. WebKit in Playwright is the Safari engine, not a real
iPhone: it cannot show notch spacing, the address bar hiding, focus zoom or the on-screen keyboard.

## What runs in parallel, and what keeps it safe

- Phase 2 is three agents; phase 3 is eight. No two tasks in a phase share a lane.
- A builder changes only its lane's files. If it needs a shared component changed, it stops and
  reports; it does not edit `components/` or `styles/`.
- Layout only. No builder changes what a screen does (login, wallet, payment, consent logic). A
  builder that finds it must stops and reports.
- At most three browser runs at once. All slots use one mock backend.
- Every builder's unit tests must still pass: about 40 test files assert the current markup.

## Verification

- After every merge: `npm run check` in `frontend/` (lint, type check, unit tests).
- Per screen and at the end: the Playwright matrix in mock mode, with the "Mock mode" pill
  confirmed first.
- Screenshots are looked at by the lead; a passing check alone is not acceptance.
- No fal.ai, Razorpay or real email call is made. `backend/.env` is not opened.
- Status reachable without the owner: **MOCK-VERIFIED in emulated browsers**. Real devices: T-364.

## Out of scope (noted, not fixed here)

Backend changes; the tracker being behind the code (T-509, T-514, T-515, T-559); the toast provider
that is never mounted; the unused `src/index.css` and `src/api.ts`; a dark theme.
